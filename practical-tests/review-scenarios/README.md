# Visual QA сценарии SV01–SV03: один чат, две последовательные части

Это отдельные, **непубликующие** проверки на недостатки по UC-VIS-004/006/008, а не заказы на создание/исправление ассетов и не UC-VIS-009 owner-review. Исторические V01–V09, их fixtures и оценочный ключ остаются неизменными. Производственные SC01–SC05 — другая группа сценариев.

## Компактная матрица

| Сценарий | Первая часть (сообщение 01) | Вторая часть (сообщение 02, тот же чат) | Смысл |
| --- | --- | --- | --- |
| **SV01 — основной, 2D** | [clip-k7, 24 кадра](SV01/01-review-k7.md) | [clip-m4, 24 кадра](SV01/02-review-m4.md) | Два связанных разворота самолётов по собственным brief |
| **SV02 — основной, 3D** | [clip-r2 + clip-t9, 48+48 кадров](SV02/01-review-jumps.md) | [clip-w8, 24 кадра](SV02/02-review-walk.md) | Прыжки vs. непрерывная ходьба: различать one-shot hold и locomotion |
| **SV03 — дополнительный, mixed** | [clip-m4, 24 кадра](SV03/01-review-2d.md) | [clip-r2, 48 кадров](SV03/02-review-3d.md) | Переключение типов visual QA после сохранения контекста |

**Основная программа — два чата (SV01 и SV02), охватывающих пять разных клипов.** SV03 запускать лишь при необходимости отдельной проверки переключения 2D→3D или сопоставления с V08/V09. Он использует **те же** m4/r2, не добавляет новых fixtures и не должен учитываться как дополнительное разнообразие набора. Не перегружать обычный чат всеми пятью клипами — для этого есть исторический нагрузочный V07.

## Порядок выполнения

1. На каждый SVxx открой **отдельный новый чат** с Fortis Repo. Отправь целиком первый промпт `01-*.md`. Дожидайся готовых per-case отчётов, реальных просмотренных полноразмерных PNG и замеров первой части.
2. После первого ответа отправь только промпт `02-*.md` **в тот же чат**. Он работает с новой группой кадров, но использует сохранённые workspace/Workfiles и не угадывает verdict из предыдущей части. Не отправляй обе части одновременно и не запускай вторую часть в новом чате.
3. В одном SVxx используется **одна уникальная** папка `/workspace/repo/Workfiles/visual-workspace-practical-tests/runs/<run-id>/`. Отдельный `review-<case>.md` на каждый клип; summary.md после обеих частей. Источники и accepted main не меняются, GitHub Issue/комментарии не создаются.
4. Только после завершения обеих частей независимый evaluator сравнивает отчёты с ожидаемыми результатами. Не раскрывай тестируемому чату `_evaluator/`, старые оценки или ожидаемую дефектность. Снимки кадров — сами доказательства; fixture names не определяют PASS/FAIL.

## Время и оценка

Первая часть — реальные UTC T0–T5 по [TIMING.md](../TIMING.md). Вторая — реальные S2.0–S2.5 с поклиповым временем, временем до первого полного PNG и отдельно ожиданием сообщения владельца. Не складывай ожидание человека с активной работой модели. Одна последовательность из двух сообщений = **один коррелированный chat-run**; несколько cases внутри него не являются независимыми повторами модели.

Состояния: `NOT RUN`, `PART1_COMPLETE_NEXT_PROMPT_PENDING`, `PART2_COMPLETE_EVALUATION_PENDING`, `PASS/PARTIAL/FAIL/INCONCLUSIVE`. Пока пользователь не отправил второе сообщение, не утверждать полного PASS.

[Отдельная матрица сценарных проверок](../REVIEW-SCENARIO-MATRIX-20261120.md) содержит статусы. Для воспроизводимости повторяй **точно такой же сценарий** в другом чистом чате, а не переписывай принятые prompts.
