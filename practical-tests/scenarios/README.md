# Scenario production acceptance — three messages, one chat, one Issue
This is an **extension** of the immutable C01–C05/A01–A05 benchmark kit, not a replacement for it. Scenario IDs are SC01–SC05; historical prompts and briefs retain their original texts and meanings. UC-VIS-008 owns test independence; UC-VIS-001–005 own production and QA; [UC-VIS-009](../../docs/use-cases/media-github-review.md#uc-vis-009) owns owner-facing Issue/revision history.
## Send exactly one message at a time
For **each** SCxx, open a different new chat with Fortis Repo:
1. Send the **entire** `SCxx/01-create-v1.md` as the initial user message. It explicitly authorizes this test's public PNG Issue publication. Wait for real source, real QA, `EXECUTED` receipt, readback, owner-viewable v1 URL, and a completed stage report. Before advancing, request a **different evaluator chat's** per-unit gate. If v1 cannot be verified, STOP; do not send a next-change prompt.
2. Open the PNG in a browser and, when ready for the planned follow-up, send only `SCxx/02-change-v2.md` in the **same chat**. This is a real new owner instruction, not a request to fix a bug. The agent must independently preserve the original task, edit source, QA and append the next sequential revision (normally v2) to the same Issue. Evaluate that submitted unit independently before proceeding. If pending/uncertain, do not jump to the next planned change.
3. Open the new PNG in a browser. Then send only `SCxx/03-change-v3.md` in the **same chat**. Verify source changes, QA, unique revision and the next version in the original Issue. Obtain independent per-unit evaluation. Record actual owner acceptance or specific additional feedback; never fabricate acceptance.
4. **After each submitted work unit**, a **different evaluator chat** checks raw Workfiles/source and Gateway readback before the runner's own summary. Save the decision under `/workspace/repo/Workfiles/visual-workspace-practical-tests/evaluations/<run-id>/<unit-id>/`. Advance only after the owner reviews the [unit gate](../_evaluator/unit-gates/README.md).
Do **not** send all three prompts to one chat in one message. Do **not** run stages 02/03 in fresh chats: remembering a task and continuing a revision is the subject of this test. A completely new run of SCxx starts from a **new chat** and gets its own Issue.

## Source and publication boundaries
The original A01–A05 briefs place all authoring output in Workfiles and do **not** authorize publication. **Only the new SCxx.01 task overrides that storage/publication rule**: the tested agent creates an isolated **registered task worktree** and source commits for each shown revision, while QA, screenshots, timing and original test-run artifacts remain in a separate unique Workfiles run directory. The remaining artistic, timing, control and QA criteria of each A0x brief stay authoritative until explicitly updated by the owner's v2/v3 message.
One logical order uses one original Fortis-created Issue. For v2/v3, the agent must use the existing source task and `prepare_visual_revision` then `append_visual_revision` with same issueNumber/baseRunId/assetId, next sequential revision, new runId/requestId and source Git SHA. Earlier body/PNG/comments remain unchanged. Use exactly 1–5 PNG per version (each <=10 MiB). Live `capabilities(refresh=True)` and scoped ALLOW must be checked before each GitHub write. No direct GitHub credentials, fallback new Issue or blind replay of unknown write.
Current public Gateway attachment workflow is PNG-only. PNG storyboards are **not** evidence of animated playback or game input: require chronological runtime captures and actual controller tests for SC03–SC05. Published GitHub images do not deliver .blend/.glb/videos or prove source merge. A real accepted source PR, exact-head CI, owner merge and guarded Windows Mirror Pull are separate from `ISSUE_REVIEWED` and must not be silently claimed.
## Status and timing
After stage 01 without actual owner feedback: `V1_OWNER_FEEDBACK_PENDING`. After v2 without third message: `V2_NEXT_CHANGE_PENDING`. On Gateway `UNCERTAIN`: `BLOCKED_UNCERTAIN` and read-only investigation of original requestId under UC-GW-009; no speculative completion.
Stage 01 records normal UTC T0–T5 under [TIMING](../TIMING.md). Follow-ups have **independent** actual clock marks S2.0–S2.5 and S3.0–S3.5; record active stage durations and owner-wait intervals separately. Never relabel a stage's T5 as completion of the three-message sequence. Without repairs, full acceptance needs three distinct source SHAs, one Issue with v1 plus v2/v3 comments, independent per-unit gates, QA and owner browser evidence. If an unplanned repair is inserted, planned unit IDs stay the same while actual revision numbers shift (e.g. v1 → repair v2 → planned change v3 → planned change v4). Require every real comment and preserve the failed first attempt; a run may be PARTIAL/FAIL/BLOCKED rather than PASS.

## Unplanned QA repairs do not replace planned owner changes

If an evaluator finds a material defect, pause the planned 02/03 message. The owner sends a **new concrete repair message** to the **same runner chat** under a separate ID like `SC01.01-R1`. The runner changes editable source, repeats QA, and if a preview was already published appends the **next** revision to the same Issue. Evaluate the repair independently before resuming the original planned message. Preserve original stage text, original first-pass score and every historical source SHA/Issue comment. See [intervention ledger](../_evaluator/unit-gates/intervention-ledger-template.md). Filenames `02-change-v2.md` and `03-change-v3.md` name logical planned messages, not absolute revision numbers after repairs.
