## Acceptance gates

- **Один новый чат = один сценарий SVxx**, содержащий последовательные пользовательские сообщения 01 → отчёт → 02 → отчёт. Не отправлять оба промпта сразу и не считать вторую часть новым cold run.
- Все исходные данные read-only. **Никаких GitHub upload/Issue**, правок fixtures, новых task worktrees и чтения `_evaluator/` проверяемым чатом. Workfiles отчёты — в одной уникальной run-папке каждого чата.
- Для каждого клипа: личный brief/capture, фактический contact sheet и все полноразмерные оригиналы по порядку, PASS/FAIL/UNCERTAIN с точными кадрами/временем и ограничениями, самостоятельный отчёт.
- Сохранить первоначальные verdict-файлы после первой части; вторая добавляет свои, итоговый summary — только после всех отдельных выводов. Отмечать FP/FN, точность локализации и придуманные дефекты после независимой оценки.
- T0–T5 по первой части, S2.0–S2.5 по второй; также per-case duration, first-full-res и длительность ожидания сообщения. Не считать время после T5 нулевым и не путать tool-returned wall-clock с UI latency.
- 2D пара содержит два близких brief; 3D прыжки имеют one-shot hold, Walk — отдельный тип поведения. Не переносить нормы одной анимации на другую.
- SV03 **повторно использует m4/r2** из основных сценариев и V08/V09: это проверка переключения контекста, не новый набор независимых кейсов. Один удачный chat-run — smoke test, не надёжность модели в процентах.
- Оценщик изучает ключ только после полной сдачи обеих частей. Если первый этап не завершён, второй не запускать. Не придумывать времена и verdict до реальных запусков.
