# UC-VIS-001 — Созданное медиа → GitHub-превью → ссылка владельцу

## Когда

В любом проекте или визуальном инструменте создан результат, который удобнее
**посмотреть**, чем разбирать из локальных путей: картинка, графика, кадры
рендера, 3D-сцена/модель, анимация, GIF или видео. Владелец ожидает ссылку
на **конкретный результат**, краткий отчёт о качестве и объяснение, что именно
можно просмотреть в браузере, а что нужно скачать/открыть в редакторе.

## Цель

После генерации сохранить проверяемое медиа, сделать понятное превью,
опубликовать его в **приватном `AlexPastukhh/visual-workspace`**, проверить
реальный GitHub URL и отправить владельцу **одну главную ссылку** с нужными
вторичными ссылками. Не подменять отсутствующий оригинальный файл его
скриншотом и не сообщать выдуманную ссылку.

## Маршрут по формату: что работает сейчас

| Результат | Как удобно посмотреть | Текущий Fortis Gateway | Что считать доставленным |
| --- | --- | --- | --- |
| Статические изображения / набор кадров | Встроенные PNG в GitHub Issue | **Реализовано:** 1–5 PNG, каждый до 10 MiB, через `github.publish_visual_review`, owner **ASK** | Issue создан, все PNG встроены, URL/receipt подтверждены |
| GIF, JPEG, SVG и другие изображения | Превью в PNG; оригинал отдельно при наличии поддержанного маршрута | Автоматический upload **только PNG**, не GIF/JPEG/SVG | Если оригинал нужен — его собственная проверенная ссылка, иначе честно «только PNG-превью» |
| Видео, запись экрана, анимация (`.mp4`, `.webm`, `.mov`) | Постер/кадры PNG в Issue + видео, которое можно воспроизвести по отдельной ссылке | PNG-постер работает; **автоматической загрузки видео этим методом нет** | Видео и воспроизведение проверены; один постер **не** подтверждает доставку видео |
| 3D-модель/сцена (`.stl`, `.glb`, `.blend` и т. п.) | PNG ракурсы/turntable; ссылка на модель и, если возможен, отдельный viewer | PNG-рендеры работают; **3D upload/viewer не реализован этим методом** | Ссылка на фактический файл/проверенный viewer; иначе пометка «только рендеры» |

GitHub сам поддерживает изображения/видео как вложения Issue; для браузерной
совместимости видео рекомендуется H.264. Веб-просмотр STL поддерживается при
**наличии файла в GitHub-репозитории** (не при одном только Issue с картинкой),
для файлов свыше 10 MiB STL viewer может не работать. Это возможности GitHub,
**не доказательство**, что Fortis уже имеет разрешённый механизм их upload.
Источники: [GitHub: attaching files](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files),
[GitHub: non-code files / STL viewer](https://docs.github.com/en/repositories/working-with-files/using-files/working-with-non-code-files).

## Как: повторяемый workflow

1. **Определить носитель и ожидание.** Уточнить, какой оригинал нужен:
   PNG-подборка, анимированное воспроизведение или интерактивная 3D-модель.
   Для 3D и видео подготовить **также** кадры PNG, но не считать их заменой
   оригинала. В разных проектах можно использовать один и тот же этот UC,
   сохраняя исходный task/worktree и QA по правилам проекта-источника.
2. **Создать файлы и идентичность запуска.** Для нового результата выбрать
   уникальный стабильный `run_id`, например `scene-demo-20261111-a`.
   Проверенные PNG для штатной автоматизации расположить в
   `/workspace/repo/Workfiles/<project>/<run_id>/.../*.png`: каждый файл обычный,
   без symlink, не более 10 MiB; не более пяти PNG на одну заявку. Оригинальные
   модели/видео можно держать рядом как рабочие артефакты, **но сам факт
   нахождения в Workfiles не публикует их**. Не включать секреты, приватные
   идентификаторы и лишние исходные данные в кадры, имена или описания.
3. **Проверить результат до upload.** Открыть реальные PNG и проверить, что
   изображено именно то, что заявлено; для видео проверить воспроизведение,
   тайминг и видимый первый кадр; для 3D — загрузку модели и минимум общий
   вид/ключевые ракурсы. Зафиксировать краткий `QA summary`, длительность
   генерации/рендера в секундах, названия и SHA-256 файлов. Не выдавать один
   заголовок файла или успешное завершение процесса за визуальную проверку.
4. **Проверить текущие возможности и способ публикации.** Аутентифицированный
   Fortis-клиент и приватный `visual-workspace` должны быть доступны. Для PNG
   использовать **только типизированный Gateway** по рецепту ниже; не
   обходить owner-ASK прямым GitHub API, CLI, PAT, HTTP-upload или ручным Git
   push от ИИ. Для видео/3D оригинала сначала нужен **отдельный поддержанный
   авторизованный маршрут** и его реальное подтверждение. Пока такого
   маршрута нет — можно опубликовать PNG-превью и явно отметить отсутствие
   видео/3D-оригинала на GitHub; если нужен оригинал, отметить задачу как
   неполную, не выдумывать download/viewer URL. **Текущий ручной вариант:**
   владелец после публикации Issue может через веб-интерфейс GitHub сам
   прикрепить поддерживаемое видео к Issue; для STL — самостоятельно
   разместить файл в приватном репозитории и открыть его GitHub blob/3D viewer.
   Это owner-side upload, **не** AI/Gateway upload; 3D `.blend`/`.glb` не
   получают автоматически браузерный viewer. ИИ затем проверяет фактическую
   ссылку через разрешённое GitHub READ и не выдаёт upload владельца за
   свой автоматический эффект.
5. **Опубликовать PNG-превью через ASK.** Стабильный `request_id` нужен для
   каждого нового запроса, а новый `run_id` — для новой редакции результата.
   Fortis сначала передаёт PNG в Gateway по machine TLS, затем создаёт
   `github.publish_visual_review` с политикой **ASK**. Владелец видит
   request/preview в [Fortis Owner Portal](http://localhost:19203) и решает,
   подтверждать ли GitHub-публикацию. `PENDING` не означает опубликованный
   Issue; `APPROVED` также не является receipt.
6. **Доказать фактическую ссылку.** После подтверждения прочитать
   `client.result(request_id)` / `client.details(request_id)` и
   фактический GitHub Issue через разрешённый Gateway READ. Только
   `EXECUTED` + receipt с URL/числом загруженных PNG и успешный readback
   Issue/встроенных ссылок дают право написать «опубликовано». Убедиться,
   что GitHub-аккаунт владельца имеет доступ к приватному репозиторию.
   Для видео/3D отдельно проверить адрес **оригинала** и возможность
   просмотра/скачивания. Если такой проверки нет — статус `PREVIEW_ONLY`.
7. **Отправить короткий результат владельцу** с ссылкой Issue, именем
   результата, кратким описанием, QA, потраченным временем и **честным
   перечнем содержимого**. При видео/3D дать отдельную проверенную ссылку
   на файл/viewer либо написать «оригинал пока не опубликован».

### Штатный вызов Fortis для PNG (не для видео и не для 3D-файла)

```python
from fortis_approvals.workflow.client import default_client

client = default_client()
# Путь и run_id должны относиться к уже созданному, проверенному PNG.
result = client.github.publish_visual_review(
    repository="visual-workspace",
    run_id="scene-demo-20261111-a",
    title="Scene demo — ракурсы и итоговый рендер",
    description="Что сделано, какая версия, что сравнивать на изображениях",
    media=[{
        "path": "/workspace/repo/Workfiles/scene/scene-demo-20261111-a/front.png",
        "name": "Front view",
    }],
    qa_summary="Проверены кадр, разрешение и соответствие сцене",
    duration_seconds=180,
    request_id="11111111-1111-4111-8111-111111111111",  # Пример UUID; для реального запуска создать новый
    reason="Передать владельцу готовое визуальное превью через приватный GitHub Issue",
)
# Не конструировать Issue URL из run_id: прочитать реальный result/receipt.
```

Пример структуры итогового сообщения **после подтверждения**:

> **Готово: Scene demo.** Открыть результат: [вставить подтверждённый
> URL GitHub Issue из receipt]. 3 PNG-ракурса, описание и QA. Время: 3 мин.
> **Оригиналы:** 3D-модель — пока только локально (на GitHub есть рендеры);
> видео — не создано. Для скачивания модели нужна отдельная публикация.

## Неизвестный исход и STOP

- `PENDING`: отправить владельцу **ссылку на Owner Portal/UUID**, а не ссылку
  на несуществующий Issue. Не создавать второй `request_id` для обхода ASK.
- `DISPATCHED`, `UNCERTAIN` или потерянный ответ после отправки: **не
  повторять** upload/publish с новым UUID или новым `run_id`. Прочитать
  `details()` с audit/`visualReview`, receipts и независимо проверить
  GitHub через Gateway READ. Возможен созданный Issue без ответа; отсутствие
  receipt не доказывает отсутствие эффекта. Дальнейшие действия —
  [UC-GW-009](https://github.com/AlexPastukhh/fortis-approvals/blob/main/docs/use-cases/incidents.md#uc-gw-009).
- `CLOSED_UNCONFIRMED`: закрытие владельцем не доказывает, что GitHub
  ничего не создал; не использовать его как разрешение на повтор.
- Нет поддержанной typed-операции / авторизации / надёжного источника
  оригинала / превью не прошло QA: **STOP** или явно `PREVIEW_ONLY`.
  Никаких вымышленных GitHub raw/download ссылок и внешних публичных хостов.
- Приватные Issue и их вложения предназначены пользователям с доступом
  к репозиторию; «ссылка готова» не означает «её увидит любой анонимно».

## Готово / критерии приёмки

**PNG:** исходный файл проверен; 1–5 PNG находятся в связанном run;
owner ASK подтверждён; Gateway вернул `EXECUTED` с настоящим Issue URL,
сохранён receipt, Issue доступен и показывает все вложенные PNG. Ссылка и
QA переданы владельцу.

**Видео / 3D:** PNG-кадры могут быть успешно опубликованы как **превью**,
но сценарий полной доставки считается завершённым только после проверки
**реального видео/модели** по отдельной ссылке и доступности нужного
viewer/download. Ручная публикация владельцем возможна через GitHub UI и
отмечается отдельно от автоматической публикации Fortis. Без этого результат помечен `PREVIEW_ONLY`, а не
`FULL_MEDIA_DELIVERED`.

**Граница проверки на дату создания UC:** метод PNG есть в исходниках
установленного Gateway и имеет тесты; реальный положительный GitHub Issue E2E
ещё не продемонстрирован. Этот UC описывает требуемую процедуру и её
acceptance, но сам по себе не устанавливает поддержку видео/3D.
