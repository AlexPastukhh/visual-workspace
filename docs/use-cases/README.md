Выбери цель, затем читай документы-владельцы по ссылкам. Реестр задаёт маршрут
и критерий завершения; общий процесс принадлежит [WORKFLOW](../../WORKFLOW.md).

2D/3D, персонаж/предмет, статичный/скелетный/процедурный результат и конкретный
редактор — варианты этих сценариев, а не отдельные юзкейсы. Создание включает
доработку существующего исходника. Не пересоздавать готовые части и не добавлять работы вне задачи:
готовый ассет можно анимировать, готовую анимацию — сразу интегрировать.

<a id="uc-vis-009"></a>

**UC-VIS-009** — [единый владелец публикации, истории версий, GitHub Issue
и обратной связи](https://github.com/AlexPastukhh/visual-workspace/blob/main/docs/use-cases/media-github-review.md#uc-vis-009).
Его не дублируют сценарии 001–008. Целевая модель — один Issue на логический
ассет/заказ: v1 создаёт Issue, v2+ добавляются комментариями в тот же Issue;
независимые заказы получают отдельные Issue. На 2026-11-19 live Gateway
предоставляет scoped `ALLOW` для `publish_visual_review` и
`append_visual_revision` в публичном `visual-workspace`. Issue #5
подтверждён для v1→v2 в одном Issue с owner browser acceptance.
Проверять capabilities перед каждым write; детали — в UC-VIS-009.
Ветку производства нельзя считать принятой только потому, что опубликована иллюстрация.

## UC-VIS-001

**Цель:** получить отдельный ассет нужного вида и назначения.

**Как:** объявить [параметры задачи](../../WORKFLOW.md#announce-the-task-parameters),
выбрать [кратчайший подходящий маршрут](../../WORKFLOW.md#2-select-the-smallest-suitable-route)
и существующие [инструменты](../../tools/README.md). Создать/изменить исходник,
получить нужный экспорт и ранний просмотр. Вложить [UC-VIS-004](#uc-vis-004)
с критериями этого ассета. При необходимости owner review передать выбранное
превью через [UC-VIS-009](#uc-vis-009) с версией и исходным SHA.
Анимацию и игру включать только по scope задачи.

**Готово:** исходник и требуемый экспорт доступны, внешний вид/масштаб/импорт
соответствуют brief; выбранные проверки пройдены и изображения просмотрены.
Изолированный просмотр не объявляется доказательством игровой интеграции.

## UC-VIS-002

**Цель:** получить нужное движение или клипы для существующего ассета/сцены.

**Как:** использовать готовый ассет; если его создание входит в задачу,
вложить [UC-VIS-001](#uc-vis-001). Объявить длительность, клипы, loop/one-shot,
форматы и прочие применимые [параметры](../../WORKFLOW.md#announce-the-task-parameters).
Выбрать [маршрут анимации](../../WORKFLOW.md#2-select-the-smallest-suitable-route),
создать движение и runtime-ресурсы. Вложить [UC-VIS-004](#uc-vis-004): проверить
нужные интервалы, границы циклов/завершение и применимые [QA-модули](../../qa/INDEX.md).
Для комментариев владельца использовать [UC-VIS-009](#uc-vis-009): PNG-кадры
не подменяют исходное видео и проверку воспроизведения.

**Готово:** анимация соответствует brief, воспроизводится из требуемого ресурса,
проверены тайминг, движение и значимые границы. Переходы контроллера и физика,
если входят в требования, доказаны последовательным runtime, а не только позами.

## UC-VIS-003

**Цель:** использовать ассет/анимацию в целевой игре с нужным поведением.

**Как:** взять существующие ресурсы; вложить [UC-VIS-001](#uc-vis-001) и/или
[UC-VIS-002](#uc-vis-002) только для требуемых доработок. Следовать
[game-ready процессу](../../WORKFLOW.md#evidence-required-for-game-ready-delivery):
подключить импорт, контроллер и игровые события, затем вложить
[UC-VIS-004](#uc-vis-004) для реального игрового поведения. Тестовый маршрут
клавиш/кнопок и agent loop — [Animation Relay](../../projects/playable-animation-demo/README.md#repeatable-input-e2e).

**Готово:** результат работает в целевой игре при нужных событиях/вводе,
проверены значимые переходы и переносимость ресурсов без QA-окружения.
Если проверена только демонстрационная игра или не проверен требуемый exported
build, это явно указано; такая проверка не подменяет недостающее доказательство.
Показать PNG/QA через [UC-VIS-009](#uc-vis-009), но для owner gameplay acceptance
сначала завершить PR/CI/merge и Mirror Pull Windows `main`, затем проверить
проект в Godot на Windows. Ссылка на Issue не доказывает запуск игры.

## UC-VIS-004

**Цель:** оценить выбранный ассет, анимацию или игровую интеграцию независимо
от остальных проектов. Может вызываться отдельно или внутри других юзкейсов.

**Как:** использовать brief и имеющуюся конфигурацию; выбрать
[достаточные доказательства](../../WORKFLOW.md#5-choose-evidence-to-match-the-acceptance-question)
и [QA-модули](../../qa/INDEX.md). Для изолированного ассета использовать
[runner и кэш](../../tools/visual_qa/README.md), для игрового поведения —
последовательный runtime целевого проекта. Просмотреть реальные изображения,
сопоставить с brief и записать выводы по [процессу ревью](../../WORKFLOW.md#6-review-images-then-spend-the-next-iteration-where-it-matters).
Проверка может выявить необходимость UC-VIS-001/002/003; исправления выполнять
в согласованном scope, затем перепроверять затронутое поведение.

**Готово:** дан обоснованный вердикт с evidence и ограничениями. Найденные
дефекты — допустимый результат проверки, но не PASS ассета. Проверка одной
фазы доказывает только её; полный результат оценивается по
[правилам завершения](../../WORKFLOW.md#7-recheck-efficiently-and-finish-the-asset).
Если вердикт/исправление нужно показать владельцу, выбрать доказательства и
передать ссылку на конкретную ревизию через [UC-VIS-009](#uc-vis-009).

## UC-VIS-005

**Цель:** выполнить комбинацию работ как одну задачу с общим результатом.

**Как:** выбрать нужные вложенные юзкейсы, повторно используя их выходы.

| Задание | Вложенный маршрут |
| --- | --- |
| Сделать ассет с анимацией | [001](#uc-vis-001) → [002](#uc-vis-002) |
| Анимировать готовый ассет и подключить в игру | [002](#uc-vis-002) → [003](#uc-vis-003) |
| Создать статичный ассет и добавить в игру | [001](#uc-vis-001) → [003](#uc-vis-003) |
| Сделать ассет, анимацию и игровое поведение | [001](#uc-vis-001) → [002](#uc-vis-002) → [003](#uc-vis-003) |

Это зависимости результата, а не требование сначала полностью отполировать
каждый этап: [раннюю интеграцию](../../WORKFLOW.md#4-get-an-early-visual-result-before-expensive-completion)
делать до дорогой детализации. Общие параметры/brief/manifest сохранять в их
[документах-владельцах](../../WORKFLOW.md#8-improve-the-workflow-without-accumulating-unnecessary-machinery),
не создавать новые копии для каждого вложенного вызова. Достаточное актуальное
QA-evidence переиспользовать; не запускать одинаковые проверки повторно из-за вложенности.

**Готово:** выполнены критерии включённых юзкейсов и общий brief; финально
проверен весь запрошенный путь. Остановиться на превью, если обещана игра, нельзя.
Для каждого логически отдельного результата выбрать свой review scope по
[UC-VIS-009](#uc-vis-009), не смешивать версии независимых заказов.

## UC-VIS-006

**Цель:** независимо просмотреть чужое или своё видео/последовательность кадров
(2D, 3D, геймплей, референс), даже когда нет Godot-проекта и asset.qa.json.
Это **просмотр**, а не создание и не обязательное исправление исходника.

**Как:** установить источник, фактический FPS/длительность, ожидаемое поведение
(если известно) и нужные эпизоды. Для уже имеющихся PNG использовать
[просмотр последовательности без исходного проекта](../../tools/README.md#external-video-and-frame-sequences).
Следовать [визуальной стратегии](../../WORKFLOW.md#5-choose-evidence-to-match-the-acceptance-question)
и [правилам просмотра](../../WORKFLOW.md#6-review-images-then-spend-the-next-iteration-where-it-matters):
сначала обзор во времени, затем хронологические полноразмерные кадры, переходы,
границы циклов и дополнительная плотная выборка при подозрении на дефект.
Для критичных кратковременных сбоев редкая выборка **недостаточна**.
Выбирать подходящие [QA-модули](../../qa/INDEX.md), не требуя игрового движка.

**Важное ограничение:** захват PNG в Godot работает; декодер произвольных
MP4/MOV/WebM в текущем контейнере не подтверждён. Нельзя объявлять, что
чат просмотрел такой файл, пока он не преобразован поддерживаемым инструментом
в реальные кадры. Без декодирования результат **BLOCKED**, а не PASS.
Для слепого теста выдавать другому чату только видео/кадры, brief и порядок
просмотра, без скрытого ключа дефектов; его ответ оценивать отдельно.

**Готово:** реально просмотрены изображения с временной привязкой, названы
наблюдения/возможные дефекты с кадрами и ограничениями. При отсутствии brief
не выносить необоснованное окончательное заключение о качестве.

## UC-VIS-007

**Цель:** принять один или несколько самостоятельных заказов на 2D/3D-ассеты,
анимации, игру или их комбинации; выполнять их по отдельности либо несколькими ИИ.

**Как:** для каждого результата выбрать [UC-VIS-001–005](#uc-vis-001)
и, если требуется, [UC-VIS-004](#uc-vis-004). До работы зафиксировать
`order-id`, список единиц результата, индивидуальные требования/brief,
нужные зависимости и **исключительные пути записи**. Одна единица может быть
только ассетом, только клипом, ассетом с клипом либо всем путём до игры.
Внутри одного заказа допускается несколько самостоятельных единиц;
каждую проверять отдельно, затем проверять общую интеграцию, если она заказана.

Для независимой работы в Asset Workbench использовать
`projects/asset-workbench/assets/<order-id>-<asset-id>/` (полный asset ID
должен укладываться в ограничения [схемы](../../tools/visual_qa/README.md#define-and-validate-an-asset)).
Это совместимо с существующим `new_asset.py`; не создавать новую схему
или общий изменяемый файл-реестр заказов. Отдельная игра может жить в своём
`projects/<unique-project-id>/`; существующую общую игру менять только
по согласованному плану интеграции.

**Несколько ИИ:** назначить каждому независимые linked worktree/ветку
по [UC-CONT-019](/workspace/repos/fortis-container/docs/use-cases/worktrees.md#uc-cont-019)
и непересекающиеся пути ассетов, сцен и игры. Один агент — единственный
владелец изменений общих `project.godot`, общих сцен/контроллеров и `tools/`;
остальные передают ему отдельные ресурсы для интеграции. Разные worktrees
изолируют незакоммиченные файлы, **но сами по себе не гарантируют бесконфликтный
merge**. Если два задания обязаны изменить один файл, выполнять такие правки
последовательно через владельца интеграции, а не параллельно.
Публикация, PR/CI и merge — только по [Fortis delivery UC](/workspace/repos/fortis-container/docs/use-cases/delivery.md#uc-cont-002).

**Готово:** каждая заказанная единица имеет свой результат, расположение,
evidence и оценку качества; общая интеграция проверена, если требовалась.
При передаче владельцу каждому независимому заказу назначить свой review thread
по [UC-VIS-009](#uc-vis-009); не публиковать незаконченные параллельные заказы
под именем одного принятого результата.
Нет неоговорённых пересекающихся путей записи или скрытых общих правок.
Критерий одного заказа не подменяет проверку других.

## UC-VIS-008

**Цель:** практически проверить новый независимый чат на чтении визуальных
доказательств и выполнении написанных заказов в 2D/3D/Godot, не раскрывая
ожидаемый ответ до завершения и измеряя фактическую длительность работы.
Готовый набор тестовых промптов уже существует; его запуск не требует автоматического AI-исполнителя.

**Принципы проектирования тестов:**

- **Action — повторяемое испытание, а не обязательно один промпт.** Описывать
  проверяемую способность, инструкцию, входы, ограничения, критерии и ожидаемые
  доказательства. Один Action может иметь несколько вариантов входных данных
  и осмысленную последовательность сообщений в одном чате. Не создавать новый
  Action только из-за другого референса или числа сообщений, если проверяемая
  способность та же; существенно другую цель проверять отдельно.
- **Совместимость с Action System без зависимости от неё.** Для новых локальных
  YAML-описаний сохранять семантику `Action` / `ActionVersion` / `ActionRun`:
  универсальные `name`, `category`, `instruction` и необязательные `workflow`,
  `schedule` — в формате существующего Action Core; специфичные для визуального
  тестирования поля — в отдельном версионируемом описании категории до появления
  соответствующей поддержки в Core. Ручное исполнение через промпты допустимо;
  регистрация в Action Registry и автоматический запуск не подразумеваются.
- **Сложность — условная характеристика самого визуального результата.** Для
  сравнимого подбора входов использовать три ориентировочных уровня: `L1` —
  простой силуэт и немного деталей; `L2` — несколько различимых частей,
  материалов или умеренная светотень; `L3` — более детализированный, но всё ещё
  обозримый объект со сложным силуэтом, несколькими уровнями деталей и
  согласованными материалами. Указывать краткое основание оценки; не превращать
  уровни в жёсткие лимиты элементов и не требовать чрезмерной детализации.
  Разные Actions могут иметь одинаковый уровень. Операция (создать, повторить,
  изменить, объединить), 2D/3D, число референсов, контекстные изменения,
  сложность интеграции и объём QA — **отдельные признаки**, а не автоматическая
  надбавка к уровню визуальной сложности.
- **Варианты и воспроизводимость.** Каждый проверяемый вариант имеет стабильный
  ID, письменные критерии, закреплённые входы/референсы с происхождением,
  правами использования, версией и контрольной суммой там, где это применимо.
  Исходный референс, задание и эталон оценщика не подменяются результатом
  исполнителя; результат должен подтверждаться настоящими исходниками и QA.
  Изменение значимых входов или правил фиксировать новой версией/вариантом,
  не переписывая историю прежних прогонов.
- **Выборка под вопрос, не полный прогон по умолчанию.** При улучшении
  инструмента брать релевантные Actions/варианты и по возможности один
  неизменный контрольный случай; для исследования пределов возможности —
  несколько входов возрастающей визуальной сложности. Нагрузка в одном чате
  и независимые повторы в новых чатах различаются. Сравнивать качество и
  стоимость только с учётом точных промптов, входов, версий инструментов,
  среды, покрытия evidence и фактических измерений, а не одной метки `L1–L3`.

**Как:** выбрать [готовое к копированию задание](../../practical-tests/README.md)
из актуальных `practical-tests/prompts-tool-safe/` либо по индексу действующих
парных сообщений и отправить его в **новом чате с Fortis Repo**. Чат читает
принятый `README.md` и применимые [UC-VIS-001–006](#uc-vis-001), после
чего независимо выполняет задание. Для визуального анализа допустимо
группировать несколько примеров с отдельным выводом по каждому. Для создания
обычно использовать **один логический заказ на чат**; его последующие изменения
отправлять отдельными сообщениями в тот же чат, если проверяется продолжение.
Каждый тестовый вариант имеет письменный brief. Проверяющий обязан действительно
открыть полноразмерные PNG, а не делать выводы из метаданных; производство
требует реальных артефактов и подтверждения в Godot.

**Результат:** отчёты, исходники тестовой работы и `timing.md` размещаются
исключительно в собственной папке `/workspace/repo/Workfiles/
visual-workspace-practical-tests/runs/<run-id>/`. Время T0–T5 измеряется
по [протоколу](../../practical-tests/TIMING.md): bootstrap, подготовка,
первый реальный визуальный результат, основная работа/QA и финальный отчёт.
Для multi-case проверок нужен отдельный вывод по каждому примеру.
Независимый оценщик сравнивает выводы с brief и закрытым ключом
только **после** сдачи; случаи внутри одного чата статистически
коррелированы, а не отдельные независимые запуски.

**Граница:** тесты UC-VIS-008 не подразумевают публикацию в GitHub и owner
Issue без отдельного поручения. Показ владельцу **реального создаваемого
результата** оформляется по [UC-VIS-009](#uc-vis-009). Live Gateway
поддерживает v1 как новый Issue и v2+ отдельными комментариями к исходному
Issue (1–5 PNG до 10 MiB каждый) при текущем scoped `ALLOW`.
Видео/GLB через этот метод не публикуются.
Старые тестовые PNG и неизменяемые briefs не модифицировать.
Ключ в `_evaluator/` защищён инструкцией, **а не правами файловой системы**:
для строгого слепого испытания оценщику нужно физически отделить ключ
от прав проверяемого чата.

**Готово:** конкретный run в Workfiles содержит воспроизводимые входные
параметры, реальные доказательства, точный PASS/FAIL/UNCERTAIN и фактически
измеренное время, а внешний оценщик документирует качество, ложные
срабатывания, пропуски и ограничения. Один успешный прогон — проверка,
но не статистическое доказательство общей надёжности.
