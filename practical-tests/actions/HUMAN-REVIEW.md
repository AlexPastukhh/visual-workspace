# Human-first review для тестовых Visual Actions

Это **локальный протокол тестирования**, а не изменение Action Core.
Для выбранных базовых Actions разрешение владельца на обязательную
GitHub-публикацию закреплено в [OWNER-ISSUE-DELIVERY](OWNER-ISSUE-DELIVERY.md);
публикация выполняется только через live-authorized typed Gateway. Исполнитель, человек и независимый чат-оценщик
— разные роли. Технические инструменты оценщика могут совпадать с инструментами
исполнителя, поэтому **визуальное принятие созданного ассета остаётся за
человеком**. Независимый чат проверяет соблюдение других требований, но не
подменяет визуальный отзыв человека и не выдаёт итоговое решение за него.

## Поле в `visual-testing.yaml`

У каждого `variants[]` рядом с `difficulty` есть обязательное поле **строгого
типа boolean** `human_review_required` (не строка и не ключ `action.yaml`):

```yaml
  - id: crystal-text-l1
    difficulty:
      level: L1
      basis: visual_detail
      rationale: Простой силуэт.
    human_review_required: true
    inputs:
      brief: practical-tests/authoring/A01-2d-static.md
      reference_pngs: []
      visual_cases: []
```

- **`true` — human-first + independent chat:** текущие VT01–VT04 и VT07–VT10
  (создание, воспроизведение, локальная правка, 2D/3D-анимации, комбинация
  референсов). **Сначала человек, потом чат**; оба отзыва необходимы.
- **`false` — chat-only:** текущие VT11/VT12 (слепые проверки *готовых* клипов
  с отдельными Action evaluator-промптами и закрытым ключом) и служебный VT15. Дополнительный
  взгляд человека допустим, но не обязателен и не меняет слепой ключ.

Флаг — **политика варианта**, независимая от уровня `L1–L3`. Даже простой L1
может требовать человека. Изменение политики фиксируется новой версией
определения, а не произвольным переопределением при запуске; сохрани exact
Git HEAD и флаг каждой попытки, чтобы не смешивать результаты разных политик.

## Порядок выполнения, строго для `human_review_required: true`

1. **Исполнитель** создаёт или изменяет ассет и сохраняет настоящий исходник,
   PNG/GLB, Godot/Blender QA, тайминги, референсы и
   `runs/<runId>/reports/units/<unitId>/submission.md` в собственном Workfiles
   run. Результат должен быть **доступен человеку для просмотра**: ссылки/
   доступные файлы полноразмерных PNG, реальные анимации (не только кадр),
   3D с несколькими ракурсами, side-by-side до/после изменений. Исходники,
   экспорт и QA не подменяются `image_gen`. Для **базовых VT01.crystal,
   VT02–VT04** Issue с реальными PNG обязательно создаётся и проверяется
   **до человеческого отзыва** по [контракту](OWNER-ISSUE-DELIVERY.md).
   Если публикация/изображения недоступны, работа ждёт доступных материалов
   со статусом BLOCKED/PENDING, а не считается принятой. Для иных вариантов
   действует их собственное явно зафиксированное условие.
2. **Человек смотрит результат ПЕРВЫМ** и даёт явную визуальную оценку:
   `ACCEPTED`, `CHANGES_REQUESTED` либо `INCONCLUSIVE`. Он может назвать
   конкретные дефекты, кадры, ракурсы и области. Отзыв фиксирует владелец/
   оркестратор в `evaluations/<runId>/<unitId>/human-review.md` по
   [шаблону](human-review-template.md) **из настоящего сообщения человека**.
   Этот документ **не содержит** ещё не существующего заключения чата.
   Молчание, факт просмотра или слова оценщика не считаются отзывом человека.
3. **Только ПОСЛЕ подтверждённого человеческого отзыва** владелец запускает
   независимый чат VT15, передавая точные `actionId`, `variantId`, `runId`,
   `unitId` и путь к `human-review.md`. До этого **VT15 нельзя запускать и
   `decision.md` создавать нельзя**. Даже `CHANGES_REQUESTED` не отменяет
   техническую проверку остальных требований: она нужна, чтобы собрать полный
   список замечаний за один цикл работы, а не тратить дополнительный прогон.
4. **Независимый чат** прочитывает сначала требования и human-review с
   конкретными отзывами, затем проверяет остальное по реальным исходникам и
   доказательствам. Он **не перепроверяет уже отмеченные человеком
   эстетические/визуальные недостатки** и не пытается опровергнуть его вкус:
   указывает `HUMAN_REPORTED / NOT_RECHECKED` со ссылкой на отзыв. Проверяет
   **все остальные** обязательные критерии: исходники, подлинность, форматы,
   экспорт/импорт, playback/loop, неизменные части, не охваченные человеком
   ракурсы/кадры и требования, время, QA и provenance. Если замечание человека
   затрагивает техническую сторону (например, отрыв детали из-за неверного
   rig), проверяет **техническую причину и другие затронутые требования**,
   не дублируя визуальное суждение. Если замечание слишком общее («плохо
   выглядит»), отмечает неясную область и продолжает независимые проверки;
   конкретику может запросить владелец.
5. Чат сохраняет **только своё нефинальное техническое заключение** в
   `evaluations/<runId>/<unitId>/decision.md` с обязательной меткой
   `scope: TECHNICAL_ONLY / NOT_FINAL`, ссылкой на human-review, отдельным
   блоком `Human-reported visual findings excluded from re-review`, перечнем
   действительно проверенных **остальных** критериев и фактическим
   техническим verdict. **Нельзя** писать `overall-review.md`, итоговый
   `PASS/ACCEPTED`, «тест пройден» или принимать human verdict от имени
   человека. Чат не редактирует runner outputs, исходный отзыв, fixture и
   GitHub.
6. **Владелец/оркестратор** после **обоих** отзывов может отдельно записать
   `evaluations/<runId>/<unitId>/overall-review.md`, связав оба первичных
   документа и конечное решение. При `CHANGES_REQUESTED` человека даже
   техническое `APPROVED` **не** даёт итогового PASS. Для VT08/VT09 каждый
   этап проходит свой human-first gate до отправки следующего сообщения в
   **тот же чат-исполнитель**. Старые решения, версии и evidence сохраняются.

При `human_review_required: false` этап человеческой оценки **пропускается**;
оценщик VT11/VT12 использует [сопоставление с закрытым
эталоном](DEFECT-SCORING.md), а не самостоятельно пересматривает клипы.
После первого unit — только процессный gate, после второго — оценка по
ключу. Там нет обязательного `human-review.md`.

## Статусы и последствия

| Что произошло | Состояние |
| --- | --- |
| Исполнитель закончил, человеческого отзыва ещё нет | **`HUMAN_REVIEW_PENDING`**; evaluator для этого варианта ещё **не запускается** |
| Человек не может увидеть существенные кадры/ракурсы | `HUMAN_REVIEW_PENDING` или человеческое `INCONCLUSIVE`; сначала обеспечить доказательства |
| Человек дал `CHANGES_REQUESTED`, чат ещё не проверил остальное | `CHAT_REVIEW_PENDING`, без общего итога; **не пропускать** оставшуюся техническую проверку |
| Человек дал `ACCEPTED`, чат ещё не проверил остальное | `CHAT_REVIEW_PENDING`, это ещё не PASS |
| Человек записал вердикт и технический `decision.md` готов | Владелец сводит оба решения; если есть замечания или пробелы, итог **не** `ACCEPTED` |
| Флаг `false` и выполнен независимый chat-only rubric | Нет обязательного человеческого gate; для VT11/VT12 итог только после полного scoring по эталону |

Никто не должен придумывать `human-review.md`, если человек ещё ничего
не оценивал. Человеческий отзыв — документируемый **визуальный вердикт**, а
не просьба оценщику «посмотреть вместо владельца». Итоговое подтверждение
человека и техническое заключение хранятся раздельно; исправления — отдельными
единицами/ревизиями, без перезаписи первой попытки.

Human review ≠ GitHub publication ≠ source merge ≠ gameplay acceptance.
В этой базовой кампании владелец **прямо потребовал** GitHub Issue для просмотра,
но факт Issue не является вердиктом. См.
[OWNER-ISSUE-DELIVERY](OWNER-ISSUE-DELIVERY.md) и
[UC-VIS-009](../../docs/use-cases/media-github-review.md#uc-vis-009).
